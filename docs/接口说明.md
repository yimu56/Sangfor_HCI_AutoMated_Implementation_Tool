## 二、三个接口的准确行为（实测）

### 1. `GET /vapi/json/cluster/network/ifaces`（**不带 node_id**）

一次返回全集群网口，**按节点分组**：

```json
{"success":1,"errcode_tracing":"","data":[
  {"node_name":"10.10.10.174","node_id":"host-a00000000001","node_status":1,
   "sriov_vtd_enable":0,
   "data":[ {"id":"channel1",...}, {"id":"eth0",...}, ..., {"id":"eth9",...} ]},
  ... 共 6 组 × 11 个网口 = 66 条
]}
```

- 分组里每个网口**不带** `node_name`/`node_id`，只有外层有。
- 与 `?node_id=xxx&refresh=1` 相比：**元素结构完全一致**（都是 `[group]`），只是返回组数不同。
  现有 `GetIfaces()` 取 `list[0]` 的写法对带参调用依然正确，无需改动。
- 无参调用**没有** `refresh=1`。改网口后的「回读确认」仍走带参 + `refresh=1`，语义不变。

### 2. `GET /vapi/json/cluster/network/vxlan-ifaces`

**扁平数组**，每个元素自带 `node_name`/`node_id`/`node_status`：

```
10.10.10.174 host-a00000000001 | id=eth1 | role=["vxlan"] | iface_mode=dpdk
                                 | mtu=1600 | vxlan_mtu=1600 | pci=0000:84:00.1
                                 | vxlan=[{gateway:"",ip:"",netmask:"",mac:"",mtu:1600}]
```

- **MTU 双值**：本接口 `mtu` = 1600（VXLAN 生效值）；而在 `/ifaces` 里同一个 eth1 是 `mtu=1500` + `vxlan_mtu=1600`（物理值 + 承载值）。界面上两个数都展示，便于对账。
- `vxlan[]` 是承载地址（当前集群为空串），`primary[].role` 也是 `vxlan`。

### 3. `GET /vapi/json/cluster/network/mgmt-ifaces`

同样是扁平数组，返回管理网口（`bond`/`channel1`）：

```
10.10.10.174 host-a00000000001 | id=channel1 | type=bond | mode=lacp-layer34
  | role=["tercom","mgmt"] | ip=10.10.10.174 | netmask=255.255.255.0
  | gateway=10.10.10.254 | members=["eth2","eth3"] | member_info=[...]
  | alias=[{"ip":"10.10.10.179","netmask":"255.255.255.0","role":"cluster_ip"}]
```

- **集群 IP 挂在某一台上**（本例是 `10.10.10.173` 的 `alias`），界面「别名IP」列会显示 `10.10.10.179(cluster_ip)` —— 也就是登录地址所在节点。
- `member_info[]` 是 bond 成员口详情（2 个）。

## 三、踩到的坑（重要）

### 坑 1：同一字段在不同接口里类型不同 —— `speed`

```
/cluster/network/ifaces      →  iface.speed            = {negotiation:1,value:1000,unknow:0,duplex:2}   (对象)
                                 member_info[].speed  = {negotiation:1,value:1000,...}                 (对象)
/cluster/network/mgmt-ifaces →  member_info[].speed   = 1000                                          (数字!)
```

`Speed` 原定义为结构体，遇到数字直接报
`json: cannot unmarshal number into Go struct field Iface.member_info.speed`，
**整个 `GetMgmtIfaces()` 解析失败、管理网口表全空**。

修法：给 `Speed` 加容错 `UnmarshalJSON`，对象 / 数字 / 带引号数字三种形态都吃（数字形态只填 `Value`）。

排查方法（可复用）：把同一字段在各接口报文里的 JSON 类型统计一遍，找出类型不一致的字段。

### 坑 2：`member_info` 是递归结构

bond 口的 `member_info[]` 里每个成员又是完整的 iface 对象（含 `speed`/`primary`/`ring_buffer`…）。
`Iface` 用 `MemberInfo []Iface` 表达即可（Go 允许自引用切片），但**必须**先修好坑 1。

### 坑 3：跨进程读控件文字要用 `WM_GETTEXT`

自动化验证时 `GetWindowTextW` 对**其它进程**的控件返回空串（Win32 已知行为），必须 `SendMessage(hwnd, WM_GETTEXT, ...)`。
另：密码框即使这样也读不到（系统刻意屏蔽），属正常。

### 坑 4：walk 的 `TabPageList.Insert(0, page)` 会导致页面空白

用 `Insert` 把页签插到首位后该页**整页空白**（连原有的「网口信息」页用同样方式插到首位也空白）。
要做「某页排第一」的效果，必须**调整 `Pages().Add()` 的调用顺序**，不能用 `Insert(0)`。
（本次验证就是这么绕过去的，正式代码未使用 Insert。）

### 坑 5：程序化切换页签不可靠

`TCM_SETCURSEL` + 补发 `TCN_SELCHANGE` 通知，在 walk 的 TabWidget 上不一定生效（walk 用 `tw.currentIndex` 缓存当前页，靠 `WM_NOTIFY` 更新）。
做 GUI 自动化验证时，别把「切页签」当可靠手段；优先让目标页本身就是第一页再截图。

## 五、如何复现验证（离线，不需要真机）

验证资产在 `C:\Users\admin\AppData\Local\Temp\hci-verify\`（临时目录，需要可自行搬走）：

```
hci-verify\
  mock\        mock.exe   深信服 vapi 模拟服务端（回放 HAR 真实报文，自签名 TLS，127.0.0.1:8443）
  mock\data\   ifaces.json / vxlan.json / mgmt.json   ← 直接从 HAR 抽出的响应体
  driver\      driver.exe  无头 GUI 驱动：改设备地址→点登录→截图（纯 syscall + PrintWindow）
  apitest\     main.go + zz_verify_test.go  协议层验证（go test）
```

协议层：

```bash
cd hci-verify/mock && ./mock.exe -addr 127.0.0.1:8443 -data data -log ../mock.log &
cd ../apitest && go test -v -count=1 .      # 4 个用例：VXLAN 网口 / 管理网口 / 一次拉全一致性 / 汇总文本
```

GUI 端到端（关键是**先把 `.sangfor-session.json` 换成 mock 地址**，让程序自己预填，比跨进程改控件文字可靠）：

```bash
# 1) 备份真实会话，写入 host=127.0.0.1:8443
# 2) 起 mock
# 3) driver.exe -exe <目标exe> -out shot.png -wait 9s
# 4) 恢复真实会话
```

> mock 服务端会校验 `CSRFPreventionToken` 与 `LoginAuthCookie`：两者缺一即返回 401 ——
> 这正是 HAR 导出时丢掉 Cookie 头会踩的那个坑，用来反向验证客户端鉴权头是否齐全。
